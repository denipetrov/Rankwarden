# Deploying Rankwarden

How to put the service and its database on a Kubernetes cluster, and how to operate them
afterwards. The reasoning behind the choices is in [DEPLOYMENT-PLAN.md](../DEPLOYMENT-PLAN.md);
this file is the procedure.

```
deploy/
  helm/mongodb/       the database: StatefulSet, users, network policy, daily backup
  helm/rankwarden/    the service: one replica, schema Job, network policy
    env/production.env   every non-secret production setting
  scripts/
    provision-digitalocean.sh   one-time: create the cluster
    create-secrets.sh           credentials into the cluster
    deploy.sh                   database, schema, service — in that order
Dockerfile            the image; also runs the schema and config commands
.github/workflows/    ci.yml (tests), release.yml (image), deploy.yml (manual deploy)
```

## What a deploy does

1. **MongoDB** comes up, then a Job creates or updates its users.
2. **The schema Job** runs `node dist/schema.main.js` as `rankwarden_schema`: it creates
   every collection and index, drops retired indexes, and verifies the result. If it fails, the release stops and the running version stays up.
3. **The service** starts as `rankwarden_app` with `DB_SCHEMA_MODE=verify`. It checks the
   structure, changes nothing, and refuses to start if step 2 was skipped.

A restart of the service therefore never touches collections or indexes. Only a deploy does.

| Database user        | Used by        | May                                                   |
| -------------------- | -------------- | ----------------------------------------------------- |
| `root`               | users Job only | everything                                            |
| `rankwarden_schema`  | schema Job     | create collections and indexes, write data            |
| `rankwarden_app`     | the service    | read and write documents; **no** index or drop rights |
| `rankwarden_backup`  | backup CronJob | read                                                  |
| `rankwarden_backend` | future backend | read                                                  |

## First deployment

Tools: `doctl`, `kubectl`, `helm` (3 or 4), `bash`.

### 1. Publish an image

```bash
git tag v1.0.0 && git push origin v1.0.0     # release.yml builds and pushes it
```

The image is `ghcr.io/denipetrov/rankwarden:v1.0.0`. The build needs to read the private
`@denipetrov/blizz-auth` package: either grant this repository access under the package's
_Manage Actions access_ setting, or add a personal access token with `read:packages` as the
`PACKAGES_TOKEN` repository secret.

### 2. Create the cluster

```bash
doctl auth init
bash deploy/scripts/provision-digitalocean.sh
```

This starts billing. The script has not been run against a real account; read it first.

Then, in the DigitalOcean control panel, create a **Spaces bucket** in FRA1 named
`rankwarden-backups` (or change `backup.s3.bucket` in `helm/mongodb/values.yaml`) and a
Spaces access key for it.

### 3. Put the credentials in the cluster

```bash
export BLIZZARD_CLIENT_ID=...  BLIZZARD_CLIENT_SECRET=...  RAIDER_IO_API_KEY=...
export GHCR_USERNAME=denipetrov  GHCR_TOKEN=...            # token with read:packages
export BACKUP_ACCESS_KEY_ID=...  BACKUP_SECRET_ACCESS_KEY=...
bash deploy/scripts/create-secrets.sh
```

Database passwords are generated by the script and exist only in the cluster. Running it
again keeps them.

### 4. Deploy

```bash
bash deploy/scripts/deploy.sh v1.0.0
```

**Only if the database was restored from a dump instead of starting empty:** the season
purge is armed in production, and it acts on the first check after a start, not only at a
rollover (`SKILLS.md` §4.8). It would retire any finished, archived season still present in
the live collections. Deploy the first time with the purge in dry-run mode, read the plan it
logs, then deploy again without the override:

```bash
RANKWARDEN_HELM_ARGS="--set-string envOverrides.SEASON_PURGE_DRY_RUN=true" bash deploy/scripts/deploy.sh v1.0.0
kubectl -n rankwarden logs deploy/rankwarden | grep -i "dry run"
```

On an empty database there is no finished season to retire, and no precaution is needed.

### 5. Check

```bash
kubectl -n rankwarden get pods
kubectl -n rankwarden logs job/rankwarden-schema | grep -i schema
kubectl -n rankwarden port-forward deploy/rankwarden 3000:3000 &
curl -s localhost:3000/health/ready
```

Readiness reports MongoDB, both upstreams, quota use and every job's state.

## Releasing a new version

```bash
git tag v1.1.0 && git push origin v1.1.0      # wait for the Release workflow
bash deploy/scripts/deploy.sh v1.1.0          # or run the Deploy workflow from GitHub
```

The service is stopped before the new one starts (`Recreate`), so there are a few seconds
with no instance. Nothing public depends on it. A job cut short by the restart resumes on
the next start.

Avoid deploying several times within an hour during an archive backfill: the Blizzard
budget is held in memory and a restart forgets the hour so far.

## Changing configuration

Edit `helm/rankwarden/env/production.env`, commit, deploy. A one-off override without a
commit:

```bash
RANKWARDEN_HELM_ARGS="--set-string envOverrides.LOG_LEVEL=debug" bash deploy/scripts/deploy.sh v1.1.0
```

CI validates the file with the service's own rules (`npm run config:check`), and a unit
test rejects a variable name the service does not read.

## The singleton rule

The service must run as exactly one instance: its schedulers, job priorities and Blizzard
quota are all in-process. The chart enforces it and offers no setting to change it:
`replicas: 1`, strategy `Recreate`, no autoscaler. **Never run `kubectl scale` on this
Deployment or attach a HorizontalPodAutoscaler to it.**

## Operations

**Logs**

```bash
kubectl -n rankwarden logs deploy/rankwarden -f
kubectl -n rankwarden logs deploy/rankwarden --previous      # the instance before a crash
```

**The service refuses to start** with "The database is not in the structure this build
needs": the schema step did not run for this version. The message lists every missing
collection and index. Deploy through `deploy.sh`, which always runs the schema step first.

```bash
kubectl -n rankwarden logs deploy/rankwarden --previous | tail -40
```

**Roll back the service**

```bash
helm -n rankwarden rollback rankwarden
```

The schema is not rolled back, and does not need to be for most changes: an older build
ignores indexes it does not know. If an older build refuses to start because the newer
one retired an index it still declares, run that older version's schema step by deploying
it with `deploy.sh <older-tag>`.

**Backups** run daily at 03:17 UTC to the Spaces bucket and are kept for 14 days.

```bash
kubectl -n rankwarden get cronjob mongodb-backup
kubectl -n rankwarden create job backup-now --from=cronjob/mongodb-backup     # take one now
```

**Restore** a backup into the running database. This overwrites documents; stop the
service first.

```bash
kubectl -n rankwarden scale deploy/rankwarden --replicas=0    # the one time scaling it is right
ROOT=$(kubectl -n rankwarden get secret mongodb-auth -o go-template='{{ index .data "root-password" | base64decode }}')
# download the archive from Spaces, then:
kubectl -n rankwarden exec -i mongodb-0 -- \
  mongorestore --uri="mongodb://root:${ROOT}@localhost:27017/?authSource=admin" \
  --gzip --archive --drop < rankwarden-<timestamp>.archive.gz
kubectl -n rankwarden scale deploy/rankwarden --replicas=1    # back to exactly one
```

**Rotate a credential.** Set the new value, run `create-secrets.sh`, run `deploy.sh`, then
restart the service so it reads the new Secret:

```bash
kubectl -n rankwarden rollout restart deploy/rankwarden
```

For a database password, first remove its key so the script generates a new one (the users
Job, which `deploy.sh` runs, then applies it). Never the administrator's: that one is fixed
when the volume is first initialised.

```bash
kubectl -n rankwarden patch secret mongodb-auth --type=json \n  -p '[{"op": "remove", "path": "/data/app-password"}]'
```

**Grow the database volume.** Raise `storage.size` in `helm/mongodb/values.yaml` and edit
the PersistentVolumeClaim to match (`kubectl -n rankwarden edit pvc data-mongodb-0`).
DigitalOcean volumes grow online; they cannot shrink.

**Connecting the backend, later.** It runs in the `backend` namespace, which both network
policies already admit.

- Service: `http://rankwarden.rankwarden.svc.cluster.local:3000`
- Database: `create-secrets.sh` prints how to read the read-only connection string.

## Trying it locally

Any local cluster works. Build the image, load it into the cluster, and override what is
DigitalOcean-specific:

```bash
docker build --secret id=npm_token,env=NPM_TOKEN -t rankwarden:local .
MONGODB_HELM_ARGS="--set storage.className=standard --set backup.enabled=false" \
RANKWARDEN_HELM_ARGS="--set image.repository=rankwarden --set imagePullSecrets=null" \
  bash deploy/scripts/deploy.sh local
```

Behind a proxy or antivirus that re-signs HTTPS, the image build needs that product's root
certificate: `--secret id=extra_ca,src=ca.pem`.

## What has been verified, and what has not

Verified on a local Kubernetes cluster (kind), with these charts and scripts unchanged:

- the full sequence: database, users, schema Job, service starting in `verify` mode;
- the service doing real work as `rankwarden_app` — a full sweep, enrichment, a Mythic+
  pass, representation snapshots — with no permission error;
- `rankwarden_app` denied index creation, index drops and collection drops; the backend
  user denied every write;
- both network policies: blocked from other namespaces and from unlabelled pods, open from
  `backend`;
- never more than one running service container during a rollout;
- a failing schema Job stopping the release with the running pod untouched;
- an unchanged redeploy leaving the pod alone; `create-secrets.sh` keeping passwords;
- backup to an S3-compatible store, and a restore of that archive.

Not verified, because each needs a real account:

- `provision-digitalocean.sh` and anything DigitalOcean-specific (block storage class,
  Spaces as the backup target);
- the three GitHub workflows, which have never run;
- pulling the image from GHCR with the `ghcr` pull secret.
